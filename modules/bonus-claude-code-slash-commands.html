Claude Code Slash Commands

Type / at the start of the prompt to run a command. Some commands are built into the tool, some are skills that ship with it, and you can write your own. This lesson covers all three, then you'll build a command of your own.

Learning objectives

By the end of this lesson you will be able to

  • Tell built-in commands, skills, and workflows apart, and say who can run each
  • Use the core commands to steer a session, manage context, and check Claude's work
  • Write a custom command with arguments and live shell output
  • Decide whether a command belongs to the project, to you, or in a plugin
The basics

Three kinds of slash command

They look the same in the menu. The difference is who wrote them and whether Claude can run them on its own.

Built-in

Part of the tool

Control the session itself: clear or compact context, switch model, manage permissions, resume an old conversation. They run instantly and don't call the model.

Skill

Bundled or custom skills

A prompt with instructions that Claude follows, such as /code-review or /loop. Your own commands are skills too. By default Claude can also load them itself when a task matches.

Workflow

Multi-step jobs

Longer jobs that spread work across subagents, such as /deep-research. Track progress with /workflows.

Reference

Every command

Search by name or by what you want to do. Arguments in [brackets] are optional and <angle brackets> are required. Not every command appears for every user: some depend on your plan, platform, or settings.

Write your own

Custom commands are now skills

A custom command is a Markdown file with optional settings at the top. The folder name becomes the command. Older files in .claude/commands/ still work. For example, .claude/commands/deploy.md gives you /deploy.

~/.claude/skills/summarize-changes/SKILL.md → /summarize-changes
---
description: Summarizes uncommitted changes and flags
  anything risky. Use when the user asks what changed,
  wants a commit message, or asks to review their diff.
---
## Current changes
!`git diff HEAD`

## Instructions
Summarize the changes above in two or three bullet
points, then list any risks...

The !`git diff HEAD` line runs before Claude reads the file. Its output takes the line's place, so Claude sees the real diff.

.claude/skills/fix-issue/SKILL.md → /fix-issue 142 high
---
description: Fix a GitHub issue by number
argument-hint: [issue-number] [priority]
allowed-tools: Bash(gh *) Bash(git *)
disable-model-invocation: true
---
Fix issue #$0 (priority: $1).

Issue details:
!`gh issue view $0`

Write a failing test first, then the fix.

An example built from the documented fields. disable-model-invocation means only you can run it, so Claude won't start it on its own.

Where the file goes

ScopePathWho gets it
Project.claude/skills/<name>/SKILL.mdEveryone who clones the repo. Commit it to share.
Personal~/.claude/skills/<name>/SKILL.mdYou, in every project on that machine.
Nested<subdir>/.claude/skills/<name>/SKILL.mdLoads when Claude first works in that folder. Useful in monorepos.
Plugin<plugin>/skills/<name>/SKILL.mdAnyone who installs the plugin. Runs as /plugin-name:skill-name.
EnterpriseManaged settings directoryEveryone in the organization.
Legacy.claude/commands/<name>.mdStill works. Subfolders namespace it: commands/frontend/component.md → /frontend:component.

If two have the same name, personal beats project, and a skill beats a .claude/commands/ file. A custom skill named like a bundled one (for example code-review) replaces it. Edits are picked up live. Run /reload-skills after creating a new skills folder.

Settings at the top of the file

FieldWhat it does
descriptionWhat it does and when to use it. Claude reads this to decide when to load it. Recommended.
argument-hintHint shown in autocomplete, e.g. [issue-number]
argumentsNamed arguments, used as $name
allowed-toolsTools pre-approved while it runs
disable-model-invocationtrue: only you can run it
user-invocablefalse: hidden from the menu, so only Claude can use it
model / effortOverride the model or effort for that turn
context: forkRun in a subagent. Pick one with agent (e.g. Explore)
nameCommand name, if not the folder name

Placeholders in the body

WriteBecomes
$ARGUMENTSEverything typed after the command
$0, $1…Single arguments, counting from 0. Quote multi-word values: /x "hello world" two
$nameA named argument from arguments
!`command`The command's output, run before Claude reads the file. A failing command stops the run. Add || true to tolerate it.
${CLAUDE_SKILL_DIR}The skill's own folder, for bundled scripts and files
${CLAUDE_PROJECT_DIR}The project root
\$A literal dollar sign

If the body has no placeholder, what you typed is added at the end as ARGUMENTS: …. You can run several skills in one message, e.g. /skill-a /skill-b do this.

From elsewhere

Plugin and MCP commands

  • Plugins can add commands. They're always namespaced as /plugin-name:command, so they never clash with yours. Manage them with /plugin, and run /reload-plugins after changes.
  • MCP servers can expose prompts that show up as commands. Manage servers with /mcp. Exact naming depends on the server. See the MCP page in the docs.
  • Agent SDK: custom commands are also available when you build your own agents with the Claude Agent SDK. They're listed in the session's start message.
Hands-on exercise · 20 minutes

Build a /commit-message command

You'll write a project command that reads your staged changes and drafts a commit message in your team's style. Use any git repository you can change. The course's lab machines work too.

  1. From the repository root, create the skill folder.

    mkdir -p .claude/skills/commit-message

  2. Create .claude/skills/commit-message/SKILL.md with this content.

    ---
description: Draft a commit message for the staged changes
argument-hint: [ticket-id]
disable-model-invocation: true
---
## Staged changes
!`git diff --cached --stat`
!`git diff --cached`

## Instructions
Write a commit message for the changes above.
- First line: under 60 characters, imperative mood
- If a ticket ID was given, start the first line with it: $ARGUMENTS
- Then a blank line and 2-4 bullets explaining why
Don't commit. Just show the message.

  3. Stage a small change, then start Claude Code in the repository and type /. Your command appears in the menu with its description.

    git add -p
claude

  4. Run it with and without an argument, and compare the results.

    /commit-message
/commit-message LAB-142

  5. Change one rule in the file (for example, ask for a one-line message only) and run it again. The edit applies straight away, with no restart.

Done when /commit-message LAB-142 prints a message whose first line starts with LAB-142 and describes your staged change. Commit the .claude/skills/ folder and everyone who clones the repository gets the command.
Check your understanding

Five questions

Answer each one, then open it to check.

1. You're halfway through a task and Claude is getting slower and losing track. Which command helps without losing the thread?

/compact. It summarizes the conversation so far and frees context. /clear would throw everything away, which is better when you're switching to an unrelated task. Use /context first to see what's taking up the space.

2. What's the difference between /code-review and /simplify?

/code-review looks for correctness bugs. /simplify looks for cleanup: duplicated code, needless complexity, inefficiency. It doesn't hunt for bugs.

3. You want a deploy command that Claude must never start on its own. Which setting do you add?

disable-model-invocation: true. Then only you can run it, by typing the command.

4. Where do you save a command so that everyone on the project gets it?

In the repository at .claude/skills/<name>/SKILL.md, and commit it. A file under ~/.claude/skills/ is personal: only you get it.

5. In the exercise, when does git diff --cached run?

Before Claude sees the prompt. The !`...` line is replaced by the command's output, so Claude reads your actual staged diff, not the command.
